【一、终极结论】
--------------------------------------------------------------------------------
1. auth3 应答(197B)的判定不发生原生层, 而是解密结果被摘要成 16 字节状态,
   存放在 VM 虚拟寄存器槽 [rbp+0x390]。判定动作 = 该槽与一次性密钥槽
   [rbp+0x430] 异或解码后, 送入判定 handler (0x5C791FC), handler 把
   期望值常量 0x3D22B75 写入栈上供 VM 取用比较。

   ★ 0x3D22B75 = 判定期望签名, 全 dump 101MB 仅出现 1 次
     (位于 0x5C79201: 48 C7 44 24 00 75 2B D2 03 = mov [rsp], 0x3D22B75)
   ★ 派生状态低 32 位 == 0x3D22B75 → "成功"路径; 否则 → 黑名单弹窗路径

2. 黑名单/成功路径在【原生层没有分叉】。递归 CFG 扫描 0x5CA1000-0x5CA3000,
   12 个入口, 命中仅 3 条 jcc, 全部是变异垃圾守卫 (目标=自身或下一条指令):
     0x5CA1904 jg 0x5CA188B (向后跳进垃圾)
     0x5CA1977 jle 0x5CA1987 (skip-junk)
     0x5CA1C67 jbe 0x5CA1C75 (skip-junk, 前轮已知)
   真正的分支在 VM 内部: "进入哪个变异块"由解释器按解密后的 VIP 数据决定。
   弹窗块 0x5CA1900-0x5CA1CA7 是一个叶子动作块 —— 黑名单时 VM 派发进入它,
   成功时根本不会进来。这就是 26 万 E8/E9/0F8x 候选 0 命中的根本原因。

3. 前轮的 "xorps xmm0,[rbp+0x430] = 197B 应答 XOR 解密" 判断需要修正:
   0x5CA1900-0x5CA2100 内 movdqa/xorps 对 16 个槽位 (0x2F0/0x300/0x310/
   0x330/0x340/0x350/0x360/0x370/0x380/0x390/0x3F0/0x400/0x410/0x420/0x430/
   0x4A0) 全部以同样模式出现 —— 这是 VMP 的【虚拟寄存器文件落盘加密】:
   每个 128 位 vregister 静止时按槽位一次性密钥加密存放, 用前 xorps 解码,
   用后重新编码。197B 载荷本身的解密在更早的 AES/解密层完成 (aes_trace 已证),
   到达此块时已是摘要后的状态值, 不是原始应答字节。

【二、弹窗块判定点逐指令语义 (核心 5 连击)】
--------------------------------------------------------------------------------
  RVA 0x5CA1C4B  66 0F 6F 85 90 03 00 00   movdqa xmm0,[rbp+0x390]
                 ; 取判定槽 V390 (auth3 派生状态, 落盘加密态)
  RVA 0x5CA1C75  48 C7 44 24 08 0D B9 9E 90   mov [rsp+8], 0xFFFFFFFF909EB90D
  RVA 0x5CA1C7E  FF 74 24 00 / 9D / 48 8D 64 24 08
                 ; push [rsp]; popfq; lea rsp,[rsp+8]
                 ; ★RFLAGS 注入: 把 0x909EB90D 当标志位集喂给下一个 handler
                 ;   (VMP "flags→常量" 混淆, 全 dump 该常量仅出现 1 次)
  RVA 0x5CA1C88  E8 61 35 FF FF             call 0x5C951EE  [枢纽 handler, 263 条入边]
                 ; 链: 0x5C951EE→0x5C9C5FE→0x5C91B20...
                 ; 主体: push -0x67FF5BE5; mov [rsp],r12; push r15; jmp ...
                 ; 语义: 消费注入的 RFLAGS, 推进 VIP/解出下一步密钥材料
  RVA 0x5CA1C8D  0F 57 85 30 04 00 00       xorps xmm0,[rbp+0x430]
                 ; ★V390 用 V430 一次性密钥解码 → 16 字节明文状态
  RVA 0x5CA1C94  E8 63 75 FD FF             call 0x5C791FC  [判定 handler]
                 ; 主体(仅 2 条真实指令):
                 ;   0x5C791FC: 48 C7 44 24 00 75 2B D2 03  mov [rsp], 0x3D22B75
                 ;   0x5C79205: E8 49 06 02 00              call 0x5C99853
                 ; 0x5C99853 = 取指枢纽(247 条入边), 链: →0x5C9BA08→0x5C999AC,
                 ; 主体含 mov rax,[rsi](VM栈弹出), adc r11b,r9b(滚动密钥),
                 ; mov [r8],r11w(回写字节码流) —— 即"从 VIP 解密下一操作数"。
                 ; 语义: 把 0x3D22B75 作为比较操作数喂给 VM, 对解码后的
                 ; xmm0 状态做等值/掩码判定 (VMP NAND 风格, 主体为 not/neg/
                 ; shl/adc 组合, 无 AES-NI/SHA 指令)
  RVA 0x5CA1C99  66 0F 7F 85 90 03 00 00   movdqa [rbp+0x390],xmm0
                 ; 判定结果重编码存回 V390
  RVA 0x5CA1CA1  E8 83 20 8C FA             call 0x563D29 [变异 stub]
                 ; stub 主体: pushfq; add [rsp+8],-0x45CA1CA6
                 ; 数学: 返回地址 0x145CA1CA6 - 0x45CA1CA6 = 0x100000000
                 ; ★call 站点地址本身参与编码 —— 返回地址被改写成常量
                 ;   0x100000000 (低 32 位相消), 证明这是 VM 续延 trampoline,
                 ;   NOP 它必然破坏 VM 簿记 (与运行时证据一致)
  RVA 0x5CA1CA7  (弹窗返回点)               运行时 MessageBoxW 返回于此
                 ; 黑名单 = 弹窗 + ExitProcess(1); 静态 dump 此处字节是
                 ; 休眠态(5字节 call), 运行时解密成 6 字节 —— 双重防静态补丁

  判定后的流程 (0x5CA1CA7 起): call 0x5C750FC (弹窗后复位) → V310/V4A0 槽
  操作 → call 0x5C99853 → call 0x5C741BE → call 0x5EC379 (VM trampoline,
  非真原生函数, 落点在另一变异页中段) —— 黑名单动作块结束后 VM 继续或退出。

【三、完整虚拟指令序列还原 (VIP 流)】
--------------------------------------------------------------------------------
0x5CA1900-0x5CA1D6C 静态流解码为 VM 动作序列 (r8=VIP, rsi=VM栈顶向下,
rbx=滚动密钥/计数, r9/r10/r11=临时; [rbp+0x2F0..0x4A0]=128位×16 虚拟寄存器):

  取V2F0 → [RFLAGS=0x909DC5FE]HUB951EE → 解码XOR→V330 → HUB99853(A) → 存V330
  → H(0x5C746DB) → 取V340 → H(0x5C759CA) → 解码XOR→V300 → 存V340
  → ★call 0x619B3B (VM trampoline, 非真原生) → 取V310 → 解码XOR→V4A0
  → H(0x5C77E42) → 存V4A0 → H(0x5C74666) → 取V330 → H(0x5C82FA9)
  → 编码XOR V330⊕V2F0 → H(0x5C752CE) → 存V2F0 → 取V300⊕V340 → 存V300
  → 取V3F0 → 解码XOR→V350 → H(0x5C75009) → 存V350
  → [RFLAGS=0x909F12AF]HUB951EE → 取V360 → 解码XOR→V400 → H(0x5C77E1D) → 存V360
  → [RFLAGS=0x10A001D6]HUB951EE → 解码XOR→V410 → H(0x5C7264C) → 存V370
  → H(0x5C7A3E0) → 取V380 → 解码XOR→V420 → H(0x5C80560) → 存V380
  → [RFLAGS=0x909F20E2]HUB951EE
  → ★取V390 → ★xorps V430 解码 → ★call 0x5C791FC (常量 0x3D22B75 判定)

【四、VM 解释器架构还原 (0x145C954FA 附近)】
--------------------------------------------------------------------------------
1. 没有静态 opcode 派发表。robust 扫描 (遇非法字节跳 1 字节续扫, 修复了
   capstone disasm 遇错即停的失真) vmp1 全段 0x5C72000-0x5CD847C:
     call rel32 = 2276 条, jmp rel32 = 1559 条, 条件 jcc = 3655 条
     指回 vmp1 内部的不同目标节点 = 2301 个 (变异 Web)
   [base+index*8] 型间接跳转全 dispatcher 心脏区仅 2 处:
     0x5C95ED8: jmp qword [rbp+rax*8]
     0x5C96AC4: jmp qword [rbx+rdi*8]
   表基址在寄存器中 (滚动解出), 静态不可枚举 —— "间接跳转表"实质不存在。
2. 六个枢纽 handler (入度统计):
     0x5C951EE (263 入边) RFLAGS 消费/VIP 推进
     0x5C99853 (247 入边) 字节码操作数解密取指
     0x5C9633F (189 入边) 派发中继
     0x5C957CF (178 入边) 派发中继
     0x5C9AEBE ( 70 入边) 派发中继
     0x5C94D55 ( 61 入边) 派发中继
   其余 ~2295 个节点入度 1-3 = 每站点专属的变异 handler 体
   (语义由 not/neg/adc/shl/shld/imul 等 NAND 风格原子组合, 逐站点去混淆)。
3. 0x145C954FA 本体: mov eax,0xFBB59189; sub rbx,1; jmp 0x5C913D8 ——
   只是 Web 中一个普通节点, 不是唯一解释器入口; "解释器"是分布式 Web。

【五、失败码计算器 RVA 0x617AD0】
--------------------------------------------------------------------------------
原生 MSVC C++ 函数 (非虚拟化):
  序言: 保存 rbx/rsi/rdi/rbp/r12-r15, lea rbp,[rsp-0x4E0], sub rsp,0x5E0,
        栈 cookie (mov rax,[rip+0xAF8782]; xor rax,rsp; 存 [rbp+0x4D0])
  0x617B08: xor esi,esi; mov [rsp+0x34],esi           ; 局部清零
  0x617B0E: lea rcx,[rip+0x4003B3] → RVA 0xA17EC8
            = ASCII "cannot get value" (前置 qword 0x0000003F5FE9283E)
  0x617B15: push rbx; call 0x5C74544 [VM]             ; 字符串送入 VM 加工
  临近原生助手 (0x617A40-0x617ACF): C++ 虚调用 trampoline (call [rax+8]),
  std::string SSO c_str() (cmp [rax+0x18],0xF; jbe), push_back(char) 内联,
  方法转发 jmp 0x45DD20
  唯一静态调用者: 0x9A75AB (call), 即"终结器"帧:
    0x9A758E call 0x9D00A4 → rdi    ┐
    0x9A7596 call 0x9D08B8 → rbx    ├→ 0x9A75AB call 0x617AD0(ecx=[rax],rdx=rbx,r8=rdi)
    0x9A759E call 0x9D08B0 → ecx    ┘
    0x9A75B0 mov ebx,eax            ; 返回值 = 失败码
    0x9A75CE mov eax,ebx; ret       ; 作为本函数结果向上传播
  语义: 把 "cannot get value" 等错误字符串经 VM 摘要成失败码。
  注意: 前轮把 0x9A75B0 当"线程入口"是误读 —— 那是 call 的返回地址,
  auth worker 抓栈时恰停在 CRT 初始化残帧上 (与本报告证伪一致)。

【六、如何让 loader 认为"成功" (按优先级)】
--------------------------------------------------------------------------------
方案 A (★新发现, 最精确): 判定点寄存器改写
  在运行时地址 base+0x5CA1C94 (call 0x5C791FC) 处下硬件执行断点
  (或 Stalker/excepthook 单步), 该时刻 xmm0 = 已解码明文状态。
  覆写 xmm0 使低 32 位 = 0x3D22B75 (其余 96 位需运行时对照成功机器取样;
  若判定只比低 32 位, 仅写低双字即可)。然后放行 —— VM 判定即"成功",
  黑名单块根本不会派发进入。比吞弹窗更根治, 且不受 MessageBoxW/ExitProcess
  拦截的次生崩溃影响。
  实施注意: 该页运行时才解密, 断点必须在执行窗口内挂 (onExecutionMoment),
  或直接断在已解密的枢纽 handler 入口 (如 0x5C791FC 运行时实体)。

方案 B: MITM 治本
  控制 auth3 应答内容, 使 AES 解密+摘要后的状态低 32 位 == 0x3D22B75。
  需先复现解密链 (密钥在 [rbp+0x430] 系一次性, 但 197B 载荷解密用 AES
  会话密钥, kr_mitm_fwd.py 基建已有; 上游 RST 问题解决后可做)。

方案 C: 既有 API 级动态等效 (kr_patch_auth3.js)
  吞弹窗 + ExitProcess 线程停车 —— 已验证可存活, 作为 A/B 的兜底。

不建议: 静态 NOP 任何字节 (0x5CA1CA1 call/0x563D29 stub/任何 jcc) ——
  运行时解密 + call 站点地址参与 VM 簿记 (返回地址→0x100000000) 双重失效。

【七、遗留不确定项 (需运行时一次取样确认)】
--------------------------------------------------------------------------------
1. 0x3D22B75 比较的精确宽度: 低 32 位等值? 64 位? 还是参与滚动校验?
   → 断 0x5CA1C94 取 xmm0 明文 + 断 0x5C99853 观察其与 0x3D22B75 的运算即可定。
2. V390 高 96 位的语义 (可能是 nonce/机器指纹混合)。
3. 0x5CA19F2 的 0x619B3B 与 0x5CA1D6C 的 0x5EC379 两个 "原生 call" 均为
   VM 续延 trampoline (落点在变异流中段, 反汇编不构成函数), 其真实动作
   在运行时页解密后才可见。
